# µPD78C14 mask-ROM reader on a Raspberry Pi Pico 2

Dumps the 16 KB internal mask ROM of the NEC µPD78C14GF (the 64-pin QFP in the
PC Engine Duo). It also works for the µPD7811 / 78C11 (4 KB), 78C12 (8 KB) and
78C18 (32 KB).

This is a port of https://github.com/devinacker/upd7811-reader (v1.0) to a Pico 2.
The upstream firmware that runs **on the NEC chip** is reused unchanged
(`upstream/upd7811-reader.bin`, embedded as `reader_rom.h`). The Pico takes over
the jobs of the upstream board's parts:

| Upstream board part | Pico 2 replacement |
|---|---|
| 27C256 EPROM holding the reader code | PIO state machine + 2 chained DMA channels serving `reader_rom.h` |
| 74HCT373 address latch | the same PIO program latches A0–A7 on ALE↓ |
| 11.0592 MHz crystal | PWM clock, 6.25 MHz, buffered by a 74HCT04 |
| reset RC + button | GP19 through the 74HCT04 (USB command `r`) |
| USB-serial adapter on PC0/TxD | UART1 RX → USB CDC, with on-the-fly Intel HEX checking |
| 7805, barrel jack, power switch | USB VBUS |

Wiring: `wiring.svg` / `wiring.png` (diagram) and `WIRING.md` (tables). Both are
generated by `tools/gen_wiring.py` from one pin table.

`tools/gen_hw.py` generates all of these from a single design table, so the
schematic and the breadboard cannot drift apart. Two checks back that up:

- `gen_hw.py` turns the breadboard layout (strips, rails, parts, jumpers) into
  nets and refuses to write anything unless they equal the design table.
- `tools/check_hw.py` asks KiCad itself (`kicad-cli`) to export the netlist and
  compares it with the design table, then runs ERC.

Current result: **49 nets match on both checks, ERC 0 errors / 0 warnings.**

```bash
python3 tools/gen_hw.py . && python3 tools/check_hw.py .
```

Differences from `wiring.svg`:

- **No series resistors.** The schematic and breadboard leave out the optional
  470 Ω resistors, because there is no room for them on a breadboard.
- **Separate pull-ups.** Each pull-up is its own 22 kΩ resistor (R1–R23); R22/R23
  are the MODE1/MODE0 ones.
- **U1 footprint.** U1 is drawn as the 900-mil DIP-64 of a QFP-64 (14×20 mm,
  1.0 mm) → DIP-64 adapter with pin N = QFP pin N. On the breadboard, mount that
  adapter **raised on stacked or long headers**: the holes under it carry the
  under-adapter jumpers and the edges of R7–R23, which go in first.

## How the dump works (the upstream trick)

1. **External boot.** MODE0 and MODE1 are pulled high through 22 kΩ. MODE0=1,
   MODE1=1 means the chip boots from **64 KB of external memory**, so the internal
   ROM is switched off. The Pico serves the reader code at 0000h, mirrored at 8000h,
   because A15 is ignored.
2. **Move to the mirror.** The reader sets MM=0Fh (full external bus, internal RAM
   on) and jumps into its 8000h mirror.
3. **Switch the ROM in.** The reader drives **its own PC7 low**. PC7 is wired to
   **MODE0**, so the MODE pins become MODE0=0 / MODE1=1. That is the normal
   "internal ROM" mode (NEC datasheet table: 78C11A/12A run with MODE0=0,
   MODE1=1). The pin is evidently checked live, not only at reset, so the mask ROM
   appears at 0000h–3FFFh while the code keeps running at 8000h+.
4. **Detect the size.** The reader compares the area below 8000h with test
   strings in its own image, which shows where the internal ROM ends (4/8/16/32 KB).
5. **Send it.** The reader sends the ROM as Intel HEX over its UART (PC0/TxD) at
   **f_clk / 96** baud. That is 115200 with the upstream 11.0592 MHz crystal and
   **65104 baud at 6.25 MHz** here; the Pico computes this automatically.

The MODE pins are also outputs (M1 and IO/M strobes when pulled up), and that is
why upstream uses pull-ups plus open-drain-style PC6/PC7 driving. Never tie them
hard to 5 V.

## Why a Pico 2, and the electrical choices

- **5 V parts.** The µPD78C14 is specified for **VDD = 5 V ±10 %** only. Its
  outputs swing to 5 V. The **RP2350's GPIOs are 5 V-tolerant** (while the Pico is
  powered); an RP2040 Pico's are not. With an RP2040 you would need level shifters
  on 18 lines, including the bidirectional AD bus.
- **Data bus.** Normal inputs on the chip need only **VIH = 2.2 V**, so 3.3 V from
  the Pico drives AD0–AD7 directly.
- **Clock and reset.** X1 and /RESET need **VIH = 0.8·VDD = 4 V**, so they go
  through a 74HCT04 running at 5 V. The datasheet wants an external clock on X1 and
  the **inverted clock on X2**, which gates 1 and 2 provide.
- **Clock range.** The clock must be **4–15 MHz** (tCYC ≤ 250 ns), so it cannot be
  slowed to a crawl. At 6.25 MHz (T = 160 ns):
  - The chip expects read data **4T − 150 = 490 ns** after /RD↓. The Pico answers in
    roughly 100–150 ns: PIO poll loop + RX FIFO → DMA → DMA → TX FIFO.
  - The address is held **T − 30 = 130 ns** after ALE↓. The PIO samples it about
    15 ns after the edge.
- **Series resistors.** The optional 470 Ω resistors limit current if something is
  mis-wired, or if the chip drives a line before the Pico's 3.3 V rail is up.
- **Reset default.** A 4.7 kΩ pull-down on GP19 keeps the chip in reset until the
  firmware runs. 4.7 kΩ, not something weaker, because of RP2350 erratum E9.

## Parts

- Raspberry Pi Pico 2 (RP2350)
- 74HCT04
- 18 × 470 Ω (optional series resistors)
- 4.7 kΩ (GP19 pull-down)
- 2 × 22 kΩ (MODE0/MODE1 pull-ups)
- 21 × 22 kΩ or resistor networks (pull-ups on PA0–7, PB0–7, PC1–5)
- 3 × 100 nF
- Optional: LED + 1 kΩ on PC5
- **QFP-64 14×20 mm (1.0 mm pitch) socket or breakout board.** The chip has to come
  off the Duo board with hot air. Reading it in-circuit is not recommended: the
  rest of the Duo board sits on those pins.

The QFP pin numbering comes from the NEC µPD78C10A/11A/12A datasheet (GF-3BE
package), which matches the µPD78C14 sheet. Pin 1 is at the dot. Pins 1–19 run
down one long side, 20–32 along the short bottom side, 33–51 up the other long
side, and 52–64 across the top. **Check with a meter before powering:** on the Duo
board, VDD (58) and VSS (26) should be on the 5 V and GND planes.

## Build

```bash
export PICO_SDK_PATH=~/Downloads/PCEngine_Duo/pico-sdk    # SDK 2.2.0 (cloned next to this project)
cmake -S . -B build && make -C build -j
# hold BOOTSEL, plug in the Pico 2, copy build/upd78c14_reader.uf2 to the RP2350 drive
```

To use a different reader image, run
`python3 tools/bin2h.py upstream/upd7811-reader.bin reader_rom.h`. To redraw the
wiring, run `python3 tools/gen_wiring.py .`.

## Use

1. Wire it up as in `wiring.png`, with the chip in its socket. Plug the Pico into USB.
2. Run:
   ```bash
   python3 tools/capture.py /dev/ttyACM0 duo_upd78c14
   ```
   This sends `r` (reset and dump), saves `duo_upd78c14.hex` and `duo_upd78c14.bin`,
   and prints the size, CRC32 and SHA1. Any terminal works too, for example
   `tio /dev/ttyACM0`, then press `r`. The Pico prints `# …` status lines and passes
   the HEX through; the LED blinks while dumping and stays solid when done.
3. **Dump 2–3 times and compare the SHA1s.** A µPD78C14 should report **16384 bytes**.

## Status

Compiles cleanly against pico-sdk 2.2.0 for `pico2` (PIO program: 21 of 32
instructions). **Not yet tested on hardware.** If the dump stalls:

- **Clock:** check X1 on a scope (≈6.25 MHz, 0–5 V).
- **Reset:** /RESET should be high after the `# … Releasing RESET` line.
- **Bus activity:** ALE should be toggling. If it is, the chip is fetching.
- **No HEX at all:** probe PC0/TxD. The reader sends nothing until the ROM is
  switched in, so a silent TxD with a busy bus means the chip is running the reader
  but has not got that far.
